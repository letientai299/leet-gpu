# Ch05 - Tiling

This file contains my analysis on how tiling speeds up naive matmul and its
hardware-dependent limitations. The pseudocode below illustrates my
understanding.

## Notation

I use $M$ (rows) and $N$ (columns) for the dimensions of the resulting matrix.

```math
C_{M \times N} = A_{M \times K} \cdot B_{K \times N}
```

## Naive matmul

```python
# naive-v1
zero(C) # initialize C to all zeros.
for y in range(0, M):
  for x in range(0, N):
    @kernel {
      for i in range(0, K):
        C[y, x] += A[y, i] * B[i, x]
    }
```

This is computationally correct, but performance is poor because:

- $A$, $B$, and $C$ remain in global memory.
- Each multiply-add performs four global memory accesses: load $A$, load $B$,
  load $C$, then store $C$ (we're ignoring compiler, hardware and cache-reuse
  optimizations magics here).
- The elements of $A$ and $B$ are each accessed $M*N*K$ times.

We can do a little better:

```python
# naive-v2
for y in range(0, M):
  for x in range(0, N):
    @kernel {
      let tmp = 0           # Keep the partial sum in a register.
      for i in range(0, K):
        tmp += A[y, i] * B[i, x]

      # tmp removes C's zero-initialization requirement.
      C[y, x] = tmp         # Access the C element once.
    }
```

This reduces global memory accesses from four per multiply-add to two. We still
perform

- $M*N*K$ multiply-adds, 2 FLOP per operation
- $2 * 4 = 8$ bytes reading for multiply-adds, so $4*2*MNK$ reading
- 4B storing for moving `tmp` into $C$, so $4MN$ B storing.

```math
\frac{2MNK}{4(2MNK + MN)} = \frac{K}{4K + 2}\ \text{FLOP/B},
```

As $K$ is quite large in practice, that approaching 0.25 FLOP/B.

## Tiling

Since access shared mem (SMEM, on-chip, near the core) is much fatser than
global mem (GMEM, off-chip, far away to the core), if we could move data to
SMEM, work with them in batch, we can speed up the kernel.

Consider a 2x2 tile. We have 2x2-threads tile, need to load 2x2 from $A$ and 2x2
from B to compute 2x2 to $C$. Thread `(0,0)` need row 0 from $A$, mean `(0,0)`
and `(0,1)` in the 2x2 load fron A, and `(0,0), (1,0)` from B. If thread `(0,0)`
load its own data, it would need to load 4 floats.

However, by working with the other 3 threads in the tile, thread `(0,0)` only
need to load 2 floats at `(0,0)` from $A$ and $B$. The other 3 threads will load
`(0,1), (1,0), (1,1)` from $A$ and $B$. Thus, global mem access reduce 50%.

Give that a full row/col has K elements, and we have just deal with 2 of theml,
we will need $K/2$ phases to really compute a cell of $C$. So, the 2x2 tile
start at `(0,0):(1,1)` in $A$ and should slide right to `(0,k-2):(1:k-1)` (let's
care about edge cases later). Similarly, the tile should slide down in the $B$
matrix.

The pseudo code would be

```python
# tile-v1
const TileSize = 2
launch<grid,blocK> {
  @kernel {
    # prepare storage on the shared mem.
    let __shared__ A_tile = new float[TileSize][TileSize]();
    let __shared__ B_tile = new float[TileSize][TileSize]();

    # for C cell index
    let gx = blockIdx.x * blockDim.x + threadIdx.x
    let gy = blockIdx.y * blockDim.y + threadIdx.y

    # for tile index
    let tx, ty = threadIdx.x, threadIdx.y

    # work in multiple phases
    let tmp = 0;
    for i in range (0, K/TileSize) {

      # in each phase, should start by copy our data to the shared mem areas
      A_tile[ty][tx] = A[gy][tx + i * TileSize]
      B_tile[ty][tx] = B[ty + i * TileSize][gx]

      # wait for other threads to copy their data, assuming tile ==  block
      __syncthreads();

      # compute
      for j in range (0, TileSize) {
        tmp += A_tile[ty][j] * B_tile[j][tx]
      }

      # wait for everyone to finish before start the making change to shared mem
      __syncthreads();
    }

    # commit the cell to global mem
    C[gy][gx] = tmp
  }
}
```

## History

Tiling is the same $ijk$ product as naive-v2, except each factor is a submatrix.
Partition $A$ into blocks $A_{yi}$ and $B$ into $B_{ix}$ whose inner sizes match
(conformable partitions). Each output tile is then

```math
C_{yx} = \sum_{i} A_{yi} B_{ix}.
```

The arithmetic is identical to elementwise matmul; only the grain size changes.
CS papers pick that grain so a tile fits a page, a cache, or a thread block's
shared memory.

[Cayley][cayley-1858] (1858) defined multiplication of arrays of scalars. He did
not treat partitioned matrices. [Laguerre][laguerre-1867] (1867) multiplied
_systèmes linéaires_ (his name for matrices) by blocks; Cayley later named that
paper as the next memoir after his own. [Turnbull and Aitken][turnbull-1932]
(1932) made partitioned matrices textbook material. The [block-matrix
product][block-matrix] is the formula above.

[cayley-1858]: https://doi.org/10.1098/rstl.1858.0002
[laguerre-1867]: http://sites.mathdoc.fr/cgi-bin/oetoc?id=OE_LAGUERRE__1
[turnbull-1932]: https://mathshistory.st-andrews.ac.uk/Extras/Turnbull_Aitken/
[block-matrix]: https://en.wikipedia.org/wiki/Block_matrix

Two independent 1969 papers:

- [McKellar and Coffman][mckellar-1969] (CACM): store and multiply by submatrix
  so a page-sized block stays in core instead of streaming whole rows. Cache
  blocking, written for virtual memory.
- [Cannon][cannon-wiki] (PhD thesis, Montana State): each cell of a 2D mesh
  holds a tile of $A$ and $B$, multiplies locally, then shifts tiles. Parallel
  tiled GEMM, not cache blocking.

[Wolfe][wolfe-1989] named compiler _tiling_ in 1987 (_Iteration Space Tiling for
Memory Hierarchies_) and expanded it in 1989: strip-mine the $ijk$ nest and
interchange so inner loops stay inside a tile. [Lam, Rothberg, and
Wolf][lam-1991] (ASPLOS 1991; Wolf $\neq$ Wolfe) made cache-blocked matmul the
textbook cache example.

Hierarchical-memory machines pushed this into libraries. [Gallivan, Jalby, and
Meier][gallivan-1987] argued that BLAS-2 is not enough and that blocked
algorithms need matrix–matrix primitives. [Dongarra, Du Croz, Duff, and
Hammarling][blas3-1990] standardized Level 3 BLAS in 1990 so `GEMM` can be a
portable blocked kernel.

Pre-CUDA GPUs had no programmer-managed on-chip store for reused tiles.
[Fatahalian, Sugerman, and Hanrahan][fatahalian-2004] (Graphics Hardware 2004)
showed GPU GEMM stayed bandwidth-bound against cache-aware CPU GEMM. The
[CUDA Programming Guide 1.0][cuda-1.0] (2007; the same kernel is already in the
0.8 beta) teaches the shared-memory tile that this chapter uses. The
[current best practices guide][cuda-best-practices] still walks through that
kernel. [Volkov and Demmel][volkov-2008] (SC 2008) kept inner tiles in registers
and approached peak; later GPU GEMM stacks (CUTLASS and friends) add more tiling
levels on the same idea.
