## Reading notes

- [x] 5.1 Importance of memory access efficiency
  - **Compute-to-global-memory-access ratio**:
    - Also called **arithmetic intensity** or **computational intensity**.
    - FLOP: floating-point operation.
    - FLOP/B: floating-point operations per byte accessed. The expression below
      performs two FLOPs and reads two 4-byte floats, giving $0.25$ FLOP/B.

    ```c
    P += A[row] * B[col]
    ```

    - This ratio gives the memory-bandwidth roof. For an A100 with $1555$ GB/s
      of bandwidth and $19.5$ TFLOP/s of FP32 throughput:
      - The expression is limited to about $389$ GFLOP/s, or $2$% of peak.
      - Arithmetic intensity must reach about $12.5$ FLOP/B to become
        compute-bound.

- [x] 5.2 CUDA memory types
  - See the [CUDA Programming Guide][cuda-memory].
  - Global memory: device-wide, readable and writable by device code, and
    accessible from the host through the CUDA APIs.
  - Constant memory: device-wide, read-only in device code, host-managed,
    cached, and limited to $64$ KB.
  - Shared memory: per block, device-only, on-chip, declared with `__shared__`.
  - Registers: per thread, device-only, on-chip scalar storage.
  - Local memory: per thread but backed by device memory. The compiler uses it
    for spills and values that cannot stay in registers.

## Ex 5.3

What type of incorrect execution behavior can happen if one forgot to use one or
both `__syncthreads()` in the kernel of Fig. 5.9?

**Answer:** Both can cause data races.

- Forgetting the first `__syncthreads()` causes threads to compute with
  incomplete data, producing incorrect results.
- Forgetting the second allows faster threads to overwrite data that slower
  threads are still using from the previous iteration, also producing incorrect
  results.

## Ex 5.4

Assuming that capacity is not an issue for registers or shared memory, give one
important reason why it would be valuable to use shared memory instead of
registers to hold values fetched from global memory? Explain your answer.

**Answer:** Shared memory allows threads in the same block to share and reuse
data. Registers, by contrast, are accessible only to their owning threads.

## Ex 5.9

A kernel performs $36$ floating-point operations and seven $32$-bit global
memory accesses per thread. For each of the following device properties,
indicate whether this kernel is compute-bound or memory-bound.

- a. Peak FLOPS $= 200$ GFLOPS, peak memory bandwidth $= 100$ GB/second
- b. Peak FLOPS $= 300$ GFLOPS, peak memory bandwidth $= 250$ GB/second

**Answer:** The kernel performs 36 FLOPs and reads $4 \times 7 = 28$ bytes per
thread, so that is $36/28 = 9/7$ FLOP/B.

- a. The hardware could do $\frac{200 GFLOPS}{100 GB/s} = 2$ FLOP/B. The kernel
  compute intensity is less than the hardware balance point, hence, this is
  memory-bound.
- b. The hardware could do $\frac{300 GFLOPS}{250 GB/s} = \frac{6}{5}$ FLOP/B,
  which is less than the kernel's compute intensity, so this is compute-bound.

## Ex 5.10

To manipulate tiles, a new CUDA programmer has written a device kernel that will
transpose each tile in a matrix. The tiles are of size `BLOCK_WIDTH` by
`BLOCK_WIDTH`, and each of the dimensions of matrix $A$ is known to be a
multiple of `BLOCK_WIDTH`. The kernel invocation and code are shown below.
`BLOCK_WIDTH` is known at compile time and could be set anywhere from $1$ to
$20$.

```c:line-numbers
dim3 blockDim(BLOCK_WIDTH, BLOCK_WIDTH);
dim3 gridDim(A_width / blockDim.x, A_height / blockDim.y);
BlockTranspose<<<gridDim, blockDim>>>(A, A_width, A_height);

__global__ void BlockTranspose(float* A_elements, int A_width, int A_height) {
  __shared__ float blockA[BLOCK_WIDTH][BLOCK_WIDTH];
  int baseIdx = blockIdx.x * BLOCK_SIZE + threadIdx.x;
  baseIdx += (blockIdx.y * BLOCK_SIZE + threadIdx.y) * A_width;
  blockA[threadIdx.y][threadIdx.x] = A_elements[baseIdx];
  A_elements[baseIdx] = blockA[threadIdx.x][threadIdx.y];
}
```

- a. Out of the possible range of values for `BLOCK_SIZE`, for what values of
  `BLOCK_SIZE` will this kernel function execute correctly on the device?
- b. If the code does not execute correctly for all `BLOCK_SIZE` values, what is
  the root cause of this incorrect execution behavior? Suggest a fix to the code
  to make it work for all `BLOCK_SIZE` values.

**Answer:**

- a. With `BLOCK_SIZE` equals to 1, the kernel is no-op. With `BLOCK_SIZE`
  larger than 1, the code can't work correctly because there are no
  `__syncthreads()` before the line that updates `A_elements[baseIdx]`, so the
  cell might take wrong value.

- b. Add `__syncthreads()` to before the `A_elements[baseIdx]` update.

## Ex 5.11

Consider the following CUDA kernel and the corresponding host function that
calls it:

```c:line-numbers
__global__ void foo_kernel(float* a, float* b) {
  unsigned int i = blockIdx.x * blockDim.x + threadIdx.x;
  float x[4];
  __shared__ float y_s;
  __shared__ float b_s[128];
  for (unsigned int j = 0; j < 4; ++j) {
    x[j] = a[j * blockDim.x * gridDim.x + i];
  }
  if (threadIdx.x == 0) {
    y_s = 7.4f;
  }
  b_s[threadIdx.x] = b[i];
  __syncthreads();
  b[i] = 2.5f * x[0] + 3.7f * x[1] + 6.3f * x[2] + 8.5f * x[3] + y_s * b_s[threadIdx.x] +
         b_s[(threadIdx.x + 3) % 128];
}
void foo(int* a_d, int* b_d) {
  unsigned int N = 1024;
  foo_kernel<<<(N + 128 - 1) / 128, 128>>>(a_d, b_d);
}
```

- a. How many versions of the variable $i$ are there?
- b. How many versions of the array `x[]` are there?
- c. How many versions of the variable `y_s` are there?
- d. How many versions of the array `b_s[]` are there?
- e. What is the amount of shared memory used per block (in bytes)?
- f. What is the floating-point to global memory access ratio of the kernel (in
  $\mathrm{OP/B}$)?

**Answer:**

- a. `i` is a local var, stored in a register, 1 per thread, so, total versions
  of `i` would be 1024.
- b. `x[]` is an thread private array, might lives in local mem or registers, 1
  per thread, so, 1024 versions.
- c. `y_s` is a shared variable, live in shared mem, 1 per block, so
  $1024/128 = 8$ versions.
- d. `b_s[]` also has 8 versions, lives in shared mem.
- e. $4 + 128*4 = 516$ bytes
- f. The kernel metrics are:
  - access 24 bytes
    - 1st `for`: load 4 floats, thus, 16 bytes.
    - load `b[i]`, 4 bytes
    - store `b[i]`, 4 bytes
  - 10 FLOP

  So $10/24$ FLOP/B
